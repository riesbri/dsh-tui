# 为什么选择 dshline

[English](comparison.md) | 中文

`dshline` 面向那些想要一个**面向 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 插件生态系统的终端原生前端**、而不是独立的终端客户端或 agent 运行时的人。

它的核心边界刻意保持狭窄：

`Harness plugin → standard capability → dshline presentation adapter → native terminal UI`

**Harness 拥有能力；dshline 只负责终端呈现。**这条边界正是选择它的原因。

## 基于 Harness 原生能力呈现

dshline 运行在 Harness 进程内，消费与当前激活的配置文件相同的权威能力约定。提供方选择、状态、持久化、生命周期、授权与策略仍由 Harness 负责；终端 UI 把这些结构化事实转化为终端呈现。

这使 dshline 能够以通用方式呈现受支持的标准能力接口。从 Work、会话投影与 agent 预设到计划中的附件，当前的呈现与未来的工作都遵循同一条边界，而不是新增提供方专用运行时。它避免了几种脆弱的替代方案：解析渲染后的文本、复制提供方连接，或维护第二套状态存储。

关于约定与权威规则，请参阅[架构](architecture.zh.md)。

## 保留终端行为的终端 UI

完成后的会话记录行进入终端真实的滚动缓冲区（scrollback），不会被移入备用屏幕或虚拟会话记录。正常的终端滚动、选择和复制因此始终可用，而 dshline 只为交互中的活动重绘有界的活动区域。

这一模型有意用全屏布局和常驻分屏，换取正常的 shell 与终端行为。[设计](design.zh.md)解释了这一选择背后的终端不变量。

## 更小的界面、更强的终端正确性

渲染器与 Harness 无关，且没有任何运行时依赖。TUI 增加的是一个小巧、可审计的呈现层，而不是另一个 agent、提供方或策略引擎。它的正确性工作清晰明确：显示列宽、Unicode 与 CJK 处理、安全的控制序列转义、键盘解码以及有界重绘行为，都可以在不需要真实模型或终端会话的情况下测试。

更小的边界也让安全审查更清晰：提问与审批在 Harness 定义的位置呈现，而工具权限与沙箱策略仍归当前激活的 Harness 配置文件管理。[安全](../SECURITY.zh.md)介绍了这一职责划分。

## 在前端之间选择

其他 Harness 前端做出了不同的取舍，包括更接近全屏的布局、不同的渲染技术栈，或客户端/服务器边界。当这些取舍重要时，请对比它们当前的文档。当你在意的属性是 Harness 原生、提供方无关的能力集成、原生滚动缓冲区，以及小巧聚焦的终端呈现架构时，请选择 dshline。

关于计划中的能力适配器与已知限制，请参阅权威[路线图](../ROADMAP.zh.md)。
